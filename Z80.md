# Z80 Port (`mandel_z80.asm`)

`mandel.asm` in this repo targets a Z180 and leans on its hardware `MLT`
(unsigned 8x8 multiply) instruction inside `l_muls_32_16x16`. Plain Z80 has
no `MLT`, so `mandel_z80.asm` is a fork with that one routine replaced by a
software multiply. Everything else - the HBIOS `RST 8` calls, the color
logic, the escape-check math - is unchanged and just as portable, since
HBIOS is the same API on any RomWBW target regardless of CPU.

Built and verified on an RC2014 Pro (`RCZ80_std` config, Z80 @ 7.372MHz,
RomWBW HBIOS/ZSDOS). Should run unmodified on any plain-Z80 RomWBW system.

## What's different from `mandel.asm`

- **`l_muls_32_16x16` is a software shift-and-add multiply.** The unsigned
  core computes a 16x16->32 product by testing one multiplier bit at a
  time and conditionally adding the multiplicand into a 32-bit
  accumulator, shifting the whole `hl:de` pair right by one each step.
  Verified against real multiplication on 2000+ random and edge-case
  (`0`, `0xFFFF`, powers of two) vectors before ever touching hardware.
- **The 16-bit loop is unrolled.** This routine is by far the hottest code
  in the program - it's called 3x per Mandelbrot iteration, and there's no
  hardware multiply to lean on anymore - so the `dec`/`jr nz` loop-control
  overhead on every one of the 16 bits was worth trading for code size.
- **RTC absence is handled gracefully.** Both `RTCGETTIM` calls now check
  the HBIOS result code (`A=0` success, nonzero e.g. `ERR_NOHW` otherwise)
  and skip the date/time and elapsed-time display on systems with no RTC
  hardware, instead of printing garbage BCD digits.
- **Fixed a latent bug inherited from the Z180 source**: the divergence
  check used `ld bc,(divergent)` - memory-indirect - instead of
  `ld bc,divergent`. `divergent` is a compile-time constant (1024), not a
  label pointing at stored data, so the indirect form was reading whatever
  2 bytes happened to sit at absolute address `0x0400`, which lands inside
  the `hsv` color table. It produced a plausible-looking render purely by
  coincidence of one particular build's memory layout, and broke (solid
  color, no shape) the moment unrelated code-size changes shifted what
  landed at that address. Worth knowing if you're porting elsewhere too.

## Performance

Software multiply is inherently slower than the Z180's hardware `MLT` -
expect this build to take noticeably longer per pixel than the timings
noted in `mandel.asm`'s own header at an equivalent clock speed. The
early-bailout optimization from this repo's `README.md` (Phase 1, item 1)
would matter less here proportionally, since the three multiplies now
dominate the per-iteration cost far more than the compare/subtract that
follows them.

## Building

Same toolchain as `mandel.asm` - HI-TECH Z80 C's assembler/linker:

```
ZAS MANDEL.ASM
LINQ -Z -N -C100H -DMANDEL.SYM -OMANDEL.COM MANDEL.OBJ
```
